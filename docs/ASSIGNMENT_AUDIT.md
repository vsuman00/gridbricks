## Vercel and Docker delivery path

Use one Vercel container for this small assignment app. [Vercel supports `Dockerfile.vercel`](https://vercel.com/kb/guide/does-vercel-support-docker-deployments) at the project root and builds it into a request-driven Function. That gives the assignment a real Docker build without splitting the app into two Vercel projects. The image must serve HTTP on `$PORT`. [Container Functions are stateless](https://vercel.com/kb/guide/does-vercel-support-docker-deployments); do not treat a runtime SQLite write as a durable import. Vercel does not deploy Docker Compose files.

1. **Container prepared:** The multi-stage [`Dockerfile.vercel`](../Dockerfile.vercel) builds the locked frontend and backend, copies the Vite output, and starts FastAPI on `0.0.0.0:$PORT`. The same-origin UI and `/api/v1` run in one process. The local two-server workflow remains available.
2. **Data packaged:** [`deployment/data/`](../deployment/data/) contains the reviewed live January SQLite snapshot, manifest and 69 raw source responses. The build checks the database, snapshot ID, input hash, manifest and every raw hash. Runtime files are read-only; browser requests do not import. A later refresh requires a new reviewed image and deployment, or a separately designed durable store.
3. **Public entry verified:** The deployed mode serves the built UI at `/`, accepts Vercel's production Host and applies separate UI/API security policies. Unauthenticated production requests returned the expected HTML and JSON.
4. **Docker tested locally:** `docker build -f Dockerfile.vercel -t gridbricks-vercel:assignment .` and `docker run --rm -p 127.0.0.1:4286:8000 -e PORT=8000 gridbricks-vercel:assignment` completed. UI, asset, health, Decision, Accuracy, CSV and a browser view check passed. The image ran as UID 10001 and the snapshot was not writable by that user.
5. **Vercel deployed:** The project uses the **Container** framework preset, repository root and GitHub `main` branch. Vercel built and pushed the image, including its verified snapshot, and assigned [gridbricks-blush.vercel.app](https://gridbricks-blush.vercel.app/). The initial **Other** preset produced a 404 and was corrected before the successful container build.
6. **Hosted release check:** Unauthenticated requests returned 200 for the home page, health, data status, Decision, full-month Accuracy and CSV. Accuracy returned 744/744 matched rows and the expected MAE; the pinned CSV had 744 rows under one snapshot ID. The Decision and Accuracy views loaded in the browser. Applying 15 January at 09:00 changed the pinned URL and showed 7,398 MW at the first delivery target. A 390-pixel viewport had no document overflow. This is hosted application evidence, not proof of future source refreshes or long-term availability.

The [Vercel container guide](https://vercel.com/kb/guide/does-vercel-support-docker-deployments) describes the Docker build and stateless runtime. The packaged SQLite file is a read-only historical snapshot. A durable refreshable database would need a separate backing service and migration; this assignment build does not provide one.

### Hosted loading follow-up, 27 October 2026

The month Accuracy link previously waited for data status before requesting analysis. Both requests now start together when the URL already contains a snapshot ID. The container also enables CDN caching for successful immutable-snapshot responses and built assets; local API responses, errors and health checks remain uncached. The client reuses number and UK-time formatters while drawing month charts. [Vercel's cache-control guidance](https://vercel.com/docs/caching/cache-control-headers) explains the `s-maxage` edge policy.

Before this change, an uncached home request took 4,193 ms in one hosted sample and returned `X-Vercel-Cache: MISS` with `Cache-Control: no-store`. After deployment, the first home request in the same probe took 825 ms and the next two cache hits took 380 and 327 ms. The first compressed full-month Accuracy request took 3,203 ms; the next two CDN hits took 105 and 109 ms. These are individual network samples, not a page-load percentile or a guarantee across regions. A cold container or a new query can still take seconds. The in-app browser loaded the 744/744 Accuracy view on two warm reloads in 217 and 251 ms without console errors. The hosted API retained the expected snapshot and MAE, and an unknown snapshot returned an uncached 404. `make check` passed 158 backend and 80 frontend tests; 20 isolated Chromium cases passed. The rebuilt Docker image passed its snapshot-integrity check and served the expected headers and 744-match response locally.
